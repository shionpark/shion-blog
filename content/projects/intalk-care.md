GA(보험대리점)가 보험 설계사 후보자를 검색·구매·온보딩하고 관리하는 양면 마켓플레이스입니다. 35개 DB 모델, 51개 서비스, 28개 컨트롤러 규모의 백엔드와 어드민 대시보드를 포함한 공급 측 전체를 혼자 설계·구현했습니다.

## 내가 만든 것

- **후보자 매칭 시스템** — 16개 필터 기반 검색, M(동기)×P(잠재력)×A(적성) 매칭 스코어, Platinum/Gold/Silver 등급 분류
- **7단계 온보딩 파이프라인** — 후보자 구매 → 3자 동의 → 매칭 → 미팅 스케줄링 → 온보딩 완료
- **크레딧 기반 과금** — 건별 크레딧 차감 구매(개별/대량), 카카오페이 단건 충전 + SID 정기결제, 환불 관리
- **실시간 채팅** — Socket.IO 기반 GA↔관리자 1:1 채팅, 알림톡·Slack 통합
- **파트너스 연동** — 파트너 신청 인바운드 API, 포트폴리오 동기화, 온보딩 상태 동기화
- **어드민 대시보드** — GA/후보자/구매/구독/온보딩/요금제/채팅/통계/분석
- **배포 파이프라인** — main push → Docker/ECR → EC2(SSM) → Prisma migrate → health check

## 매칭 스코어 설계

검색 결과에 후보자가 30명 나와도 누구부터 봐야 할지 판단할 기준이 없었습니다. 프로필 열람에 크레딧이 소모되는 과금 모델이라 "열어봐야 아는" 구조에서 구매 전환이 낮았습니다.

후보자 데이터를 3개 축(동기·잠재력·적성)으로 나누고 각 축에 가중치를 적용해 종합 스코어를 산출했습니다. 스코어 계산은 복잡하고 원본 데이터 변경 빈도가 낮아서 실시간 대신 배치로 돌리되, 후보자가 새 정보를 입력하면 이벤트 기반으로 즉시 재계산합니다. 검색 결과에는 등급과 축별 스코어를 함께 노출해서, 프로필을 열기 전에 적합도를 예측할 수 있게 했습니다.

## 양면 마켓플레이스 상태 동기화

파트너스(수요 측)와 케어(공급 측)는 별도 서버·DB로 운영됩니다. 파트너 신청은 파트너스 → 케어로 API 인바운드 처리하고, 온보딩 상태는 파트너스가 30분 간격으로 케어 DB를 폴링하는 구조입니다. 실시간 동기화가 이상적이지만, 두 시스템의 배포 주기가 다르고 장애 격리가 중요해서 eventual consistency를 선택했습니다.

## 3자 동의 기반 매칭 분기

3자 동의 여부에 따라 즉시 매칭과 내부 승인 후 예약 매칭으로 분기합니다. 법적 요건(개인정보 제3자 제공 동의)과 비즈니스 로직(매칭 속도)을 동시에 충족해야 해서, 동의 상태를 매칭 파이프라인의 분기 조건으로 설계했습니다.
