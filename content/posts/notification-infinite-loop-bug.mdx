## 문제 발견

인톡 파트너스에서 관리자가 사용자에게 채팅을 보내면, 일정 시간 미읽음 상태일 때 알림톡을 발송하는 기능이 있었습니다. 어느 날 한 사용자에게 알림톡이 하루에 수십 건씩 발송되고 있다는 리포트가 들어왔습니다.

## 원인: TTL과 크론 주기의 드리프트

기존 로직은 이렇게 동작하고 있었습니다:

1. 30분마다 크론이 실행되어 3시간 이상 미읽음 채팅방을 조회
2. 해당 채팅방에 알림톡 발송
3. Redis에 `chat:unread-alimtalk:{roomId}` 키를 **24시간 TTL**로 저장해 중복 방지

얼핏 보면 문제없어 보입니다. 24시간 동안은 같은 채팅방에 알림톡이 재발송되지 않으니까요.

하지만 **시간 드리프트**가 문제였습니다:

```
Day 1: 10:00 발송 → TTL 만료 시각: Day 2 10:00
Day 2: 10:30 크론 실행 → TTL 만료됨 → 재발송 → 새 TTL: Day 3 10:30
Day 3: 11:00 크론 실행 → TTL 만료됨 → 재발송 → 새 TTL: Day 4 11:00
```

크론은 30분 간격으로 실행되지만, TTL은 정확히 24시간 후에 만료됩니다. 매일 최대 30분씩 밀리면서 TTL 만료 직후 크론이 실행되고, 다시 알림톡이 발송되는 루프가 생긴 것입니다.

사용자가 메시지를 읽지 않는 한, **매일 1회씩 무한으로 알림톡이 발송**되는 구조였습니다.

## 근본 원인

문제의 본질은 "중복 방지"라는 설계 의도와 "TTL 기반 만료"라는 구현 사이의 불일치였습니다.

- **의도**: 한 채팅방에 대해 알림톡을 한 번만 보내고 싶음
- **구현**: 24시간 TTL로 "잠깐" 중복을 막음
- **결과**: 24시간 후 TTL이 만료되면 "한 번만"이라는 제약이 사라짐

TTL을 더 길게 잡으면? 사용자가 메시지를 읽고 다시 미읽음이 생겼을 때 정상적인 알림이 차단됩니다. TTL 자체가 이 문제의 올바른 해결책이 아니었습니다.

## 재설계: 2단계 상태 머신

"횟수 제한" 방식에서 "상태 전이" 방식으로 근본적으로 바꿨습니다.

### 설계 원칙

- 알림톡은 **최대 2회**만 발송 (리마인드 1회 + 종료 안내 1회)
- 각 단계는 Redis 키로 **상태**를 관리 (TTL 없음)
- 사용자가 메시지를 읽으면 상태를 초기화

### 플로우

```
[미읽음 1시간 경과]
    → 1단계: 리마인드 알림톡 발송
    → Redis: chat:unread-reminder:{roomId} = "sent"
    → 채팅방에 종료 예고 메시지 삽입

[종료 예고 후 1시간 경과]
    → 2단계: 종료 안내 알림톡 발송
    → 채팅방 상태를 CLOSED로 변경
    → Redis 키 삭제

[사용자가 메시지를 읽음]
    → Redis 키 삭제 (상태 초기화)
```

### 핵심 변경

```typescript
// Before: TTL 기반 중복 방지 (드리프트 발생)
const redisKey = `chat:unread-alimtalk:${room.id}`;
await this.redisService.set(redisKey, '1', 60 * 60 * 24); // 24h TTL

// After: 상태 기반 (TTL 없음, 명시적 삭제)
const reminderKey = `chat:unread-reminder:${room.id}`;
await this.redisService.set(reminderKey, 'sent'); // TTL 없음
```

TTL을 없앤 것이 핵심입니다. 상태의 생명주기를 시간이 아니라 **사용자 행동(메시지 읽음)** 에 연결했습니다.

## 크론 주기도 조정

기존 30분 → 10분으로 변경했습니다. 1시간 미읽음 기준이기 때문에 10분 간격이면 최대 10분 지연으로 알림이 발송됩니다. 30분 간격은 사용자 경험상 너무 느렸습니다.

## 교훈

**TTL과 크론 주기를 조합할 때는 드리프트를 반드시 고려해야 합니다.** 두 타이머가 독립적으로 동작하면 매 주기마다 미세한 시간차가 누적되고, 이것이 의도하지 않은 동작을 만듭니다.

더 근본적으로는, "중복 방지"와 "상태 관리"는 다른 문제입니다. TTL 기반 중복 방지는 "일정 시간 동안만" 유효한 단기 보호이고, 비즈니스 로직의 상태 전이는 명시적인 상태 머신으로 관리하는 것이 안전합니다.
