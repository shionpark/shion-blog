## 문제 발견

보장분석 기능(`/insurance/coverage`)을 배포한 뒤, 수치가 잘 찍히고 있는지 확인하려고 세 곳의 트래킹 데이터를 열어봤습니다.

| 소스 | PV |
|---|---|
| 자체 관리자 대시보드 | 19 |
| GA4 | 7 (3일 누적) |
| Mixpanel | **0** |

하나의 페이지를 세 곳에서 추적하고 있는데, 세 수치가 모두 다릅니다. 자체 대시보드는 19인데 GA4는 3일치를 합쳐도 7이고, Mixpanel은 아예 0입니다.

GA4와 자체 대시보드의 차이는 어느 정도 예상할 수 있습니다. 수집 방식이 다르니까요. 하지만 Mixpanel이 0건인 것은 "차이"가 아니라 "고장"입니다.

세 곳 중 하나만 틀렸다면 그 하나를 고치면 됩니다. 하지만 세 수치가 전부 다르면 "어디가 맞는 거지?"부터 시작해야 합니다. 기준점이 없는 상태에서 각 소스의 수집 경로를 하나씩 따라가며 원인을 추적했습니다.

### 트래킹 아키텍처 개요

원인을 설명하기 전에, 세 트래킹이 어떤 경로로 데이터를 수집하는지 정리하겠습니다.

```
[사용자 브라우저]
  ├─ gtag.js ─────────────────────→ GA4 (Google 서버 직접)
  ├─ Mixpanel SDK → /mp/[...path] → Mixpanel (자체 프록시 경유)
  └─ fetch('/api/page-tracking') ─→ 자체 DB (BE API 경유)
```

GA4는 gtag 스니펫이 Google 서버로 직접 이벤트를 보냅니다. Mixpanel은 광고 차단기를 우회하기 위해 자체 Next.js API 라우트를 프록시로 경유합니다. 자체 트래킹은 BE API를 호출해서 DB에 적재합니다.

세 경로가 완전히 독립적이기 때문에, 어느 한 곳에 문제가 생겨도 나머지에는 영향이 없습니다. 반대로 말하면, 문제가 생겼을 때 어디가 고장인지 교차 검증이 가능하다는 뜻이기도 합니다.

## 원인 분석

### 원인 1: Mixpanel 0건 — 프록시의 IP 차단

Mixpanel 프록시(`/mp/[...path]/route.ts`) 내부에 사내 IP를 차단하는 로직이 있었습니다:

```typescript
// /mp/[...path]/route.ts 내부
if (EXCLUDED_IPS.includes(clientIp)) {
  return NextResponse.json({ status: 1 });
}
// 사내 IP가 아닐 때만 Mixpanel 서버로 포워딩
```

사내 IP에서 들어온 요청은 Mixpanel 서버로 포워딩하지 않고, `{"status": 1}`을 응답하면서 이벤트를 조용히 버립니다. `status: 1`은 Mixpanel의 정상 응답 포맷이라, SDK 입장에서는 "성공적으로 전송됨"으로 인식합니다. 브라우저 콘솔에도 에러가 뜨지 않습니다.

배포 후 테스트를 전부 사무실에서 했습니다. 개발팀이 사무실에서 페이지를 열고 "Mixpanel에 이벤트가 안 찍힌다"고 본 것은, 프록시가 정상적으로 사내 트래픽을 차단한 결과였습니다. 외부 네트워크에서 접속한 실제 사용자의 이벤트는 정상 기록되고 있었습니다.

이것만으로도 0건의 원인이 설명되지만, 추가로 한 가지 더 있었습니다. 보장분석 기능의 전체 플로우는 `/insurance` → `/insurance/preview` → `/insurance/coverage` 세 페이지로 구성되는데, 앞 두 페이지에 대한 Mixpanel 이벤트 매핑이 누락되어 있었습니다. `/insurance/coverage`에는 이벤트를 등록했지만, 같은 플로우의 진입 페이지와 미리보기 페이지는 빠뜨린 것입니다.

프록시 IP 차단 + 이벤트 매핑 누락이 겹치면서, Mixpanel에서는 보장분석 플로우 전체가 "존재하지 않는" 것처럼 보였습니다.

### 원인 2: BE 날짜 필터 — UTC/KST 불일치

자체 관리자 대시보드의 19라는 수치도 정확한지 의심스러웠습니다. page-tracking API의 날짜 필터 코드를 확인해 보니 이렇게 되어 있었습니다:

```typescript
// 수정 전: UTC 자정 기준
const startDate = new Date(`${dateString}T00:00:00Z`);
const endDate = new Date(`${dateString}T23:59:59Z`);
```

`dateString`이 `"2026-07-13"`이면, UTC 기준으로 7월 13일 00:00:00부터 23:59:59까지를 조회합니다.

```
조회 조건: date = "2026-07-13"

UTC 기준 범위: 2026-07-13 00:00:00 ~ 2026-07-13 23:59:59
KST로 환산하면: 2026-07-13 09:00:00 ~ 2026-07-14 08:59:59
```

관리자가 "7월 13일" 데이터를 조회하면, KST 기준 7월 13일 오전 9시부터 7월 14일 오전 9시까지의 데이터를 보게 됩니다. 00:00~09:00 사이 새벽 데이터는 전날 날짜에 집계되고, 당일 데이터에는 다음 날 새벽 데이터가 섞여 들어갑니다.

이 문제가 까다로운 이유는, 수치가 "0"이 아니라 "그럴듯한 숫자"로 나온다는 것입니다. 19건이라는 숫자를 보고 "이상하다"고 느끼기 어렵습니다. 새벽 시간대 트래픽이 적은 서비스라면 오차도 작아서, 교차 검증을 하지 않는 한 발견이 거의 불가능합니다.

이 문제는 page-tracking API의 날짜 필터 4곳 — 일별 조회, 기간별 조회, 페이지별 집계, 전체 통계 — 모두에 존재했습니다.

## 해결

### 1단계: FE 이벤트 정비 (FE-CHORE-020, PR #58)

먼저 프론트엔드 쪽을 정리했습니다.

- 사용하지 않는 dead code 4개 제거
- `/insurance`, `/insurance/preview` 페이지뷰에 대한 Mixpanel 이벤트 매핑 2개 추가

PR #58로 머지·배포했습니다.

이 과정에서 한 가지 삽질이 있었습니다. GTMProvider에 SPA 트래킹 로직을 직접 추가하는 시도를 했습니다. Next.js App Router 환경에서 클라이언트 사이드 라우팅 시 GA4 페이지뷰가 누락될 수 있다는 판단이었습니다.

```typescript
// GTMProvider에 추가했던 코드 (이후 revert)
useEffect(() => {
  const handleRouteChange = (url: string) => {
    window.gtag?.('event', 'page_view', { page_path: url });
  };
  // pathname 변경 감지...
}, [pathname]);
```

하지만 GA4 콘솔에서 확인해 보니, Enhanced Measurement가 이미 History API 변경을 감지해서 SPA 페이지뷰를 자동 처리하고 있었습니다. 수동으로 추가한 트래킹과 중복 발화되어 PV가 2배로 잡히는 것을 확인하고 바로 revert했습니다.

기존 도구가 이미 처리하고 있는 것을 모르고 중복 구현하는 실수는 생각보다 흔합니다. 수정하기 전에 현재 동작을 먼저 확인하는 습관이 중요합니다.

### 2단계: BE 날짜 필터 통일 (BE-BUG-019, PR #59)

UTC/KST 불일치를 해결하기 위해 `getKstStartDate()` 헬퍼를 만들었습니다.

```typescript
function getKstStartDate(dateString: string): Date {
  // "2026-07-13" → KST 자정(00:00) = UTC 전날 15:00
  const KST_OFFSET_MS = 9 * 60 * 60 * 1000;
  const utcMidnight = new Date(`${dateString}T00:00:00Z`);
  return new Date(utcMidnight.getTime() - KST_OFFSET_MS);
}
```

핵심은 입력받은 날짜 문자열을 "사용자가 의도한 KST 자정"으로 해석하는 것입니다. `"2026-07-13"`이 들어오면 KST 7월 13일 00:00:00, 즉 UTC 7월 12일 15:00:00을 반환합니다.

기존 코드에서 `new Date(dateString)`으로 직접 변환하던 4곳을 모두 이 헬퍼로 교체했습니다:

```typescript
// Before: 각 쿼리에서 직접 변환
const startDate = new Date(`${dateString}T00:00:00Z`);

// After: 헬퍼로 통일
const startDate = getKstStartDate(dateString);
```

날짜 변환 로직이 한 곳으로 모이면서, 향후 타임존 관련 수정이 필요할 때도 헬퍼 하나만 고치면 됩니다. PR #59로 머지·배포했습니다.

### 3단계: 교차 검증

배포 후 세 소스를 직접 교차 검증했습니다. 각 소스별로 데이터를 실제로 꺼내서 비교하는 과정이 필요합니다.

**Mixpanel** — Signal Analysis API로 이벤트를 조회했습니다. 수정 전에는 보장분석 관련 이벤트가 0건이었는데, 배포 후 외부 네트워크에서 접속하여 2건이 정상 기록되는 것을 확인했습니다. 프록시를 경유한 이벤트가 Mixpanel 서버에 도달하고 있음이 증명되었습니다.

**GA4** — GA4 Data API를 호출해서 `/insurance/coverage` 페이지뷰 수치를 조회했습니다. GA4는 데이터 처리에 24~48시간 지연이 있을 수 있어서, 리얼타임 리포트와 일반 리포트를 둘 다 확인했습니다.

**자체 DB** — 프로덕션 DB에 SSH 터널로 접속해서 page_tracking 테이블을 직접 쿼리했습니다. KST 기준 날짜 필터가 올바르게 적용되어, 수정 전과 다른(정확한) 수치가 나오는 것을 확인했습니다.

세 소스 모두에서 이벤트가 기록되고 있었고, 수치 차이가 설명 가능한 범위 안에 있음을 확인하고 마무리했습니다.

## GA4 > BE 수치 차이는 정상인가

버그를 모두 수정한 후에도, GA4 수치가 자체 DB보다 일관되게 높은 것이 관찰되었습니다. 이것도 버그인지 확인이 필요했습니다.

분석 결과, 이 차이는 구조적인 것이었습니다. BE 쪽에서 수치가 줄어드는 요인이 세 가지 있습니다.

**1. IP 필터링**

BE 트래킹은 `TRACKING_EXCLUDED_IPS` 환경변수에 등록된 사내 IP를 필터링합니다. 개발팀이 테스트하면서 발생시킨 페이지뷰는 BE에 기록되지 않습니다. 반면 GA4에는 이 필터가 없어서 사내 트래픽까지 전부 집계됩니다.

**2. React 하이드레이션 전 이탈**

Next.js가 서버에서 HTML을 렌더링한 후, 클라이언트에서 JS 번들이 로드·실행되어야 BE 트래킹 API 호출이 발생합니다. 번들 로드 전에 이탈하는 사용자는 BE에 기록되지 않습니다. GA4의 gtag 스니펫은 인라인 스크립트로 번들보다 먼저 실행되므로, 이 구간의 방문도 잡아냅니다.

**3. API 실패 시 silent drop**

BE 트래킹은 `fetch`로 자체 API를 호출하는 방식입니다. 네트워크 불안정, 서버 에러, 타임아웃 등으로 요청이 실패하면 재시도 없이 누락됩니다. GA4 SDK는 IndexedDB 기반 큐와 자체 재시도 메커니즘을 갖고 있어 네트워크 불안정에 더 강합니다.

이 세 요인을 종합하면, GA4 > BE는 구조적으로 발생하는 정상 범위의 차이입니다. 오히려 BE 트래킹은 사내 트래픽을 제외하고, JS가 완전히 로드된 "실제 사용 세션"만 기록하기 때문에 "서비스를 실제로 사용한 사용자"에 더 가까운 지표입니다.

결론적으로 GA4는 전체 트래픽 볼륨 파악용, BE는 실사용자 행동 분석용으로 역할을 분리하는 것이 적절합니다. 두 수치를 무리하게 일치시키려고 하면 오히려 각각의 장점을 잃게 됩니다.

## 교훈

### 멀티 트래킹의 목표는 "일치"가 아니라 "설명 가능한 차이"

GA4, Mixpanel, 자체 DB는 각각 수집 시점, 필터링 조건, 전송 방식이 다릅니다. 세 수치가 정확히 같을 수는 없고, 같다면 오히려 의심해야 합니다.

중요한 것은 차이의 원인을 설명할 수 있는지 여부입니다. 이번 사례에서 Mixpanel 0건은 "설명 불가능한 차이"였고, 그래서 버그였습니다. 반면 GA4 > BE는 구조적 원인이 명확한 "설명 가능한 차이"였고, 수정 대상이 아니었습니다.

새로운 트래킹을 추가할 때마다 "이 소스와 다른 소스의 차이는 무엇 때문인가"를 문서화해 두면, 나중에 수치 이상이 발생했을 때 버그인지 정상 차이인지 빠르게 판단할 수 있습니다.

### 사내 IP 차단은 양날의 검

사내 트래픽을 걸러내는 것은 데이터 정확도를 위해 필요하지만, 동시에 개발팀의 테스트 결과를 왜곡합니다. 이번 사례에서 Mixpanel 0건이 "정상"으로 보였던 이유가 바로 이것입니다. 프록시가 정상적으로 동작한 결과가 "이벤트 0건"이었으니, 누구도 의심하지 않았습니다.

사내 IP 차단이 적용된 환경에서는 두 가지 중 하나를 마련해야 합니다. 외부 네트워크에서 검증하는 프로세스를 만들거나, 개발 모드에서는 IP 차단을 우회할 수 있는 플래그를 두는 것입니다.

### 타임존은 매번 등장한다

서버가 UTC로 동작하는 환경에서 KST 기준 리포트를 제공한다면, 날짜 필터가 "어떤 자정"을 기준으로 하는지 반드시 확인해야 합니다. 이번처럼 9시간치 데이터가 조용히 다른 날짜로 밀려나는 문제는, 수치를 교차 검증하지 않으면 오래도록 발견되지 않습니다. 새벽 시간대 트래픽이 적을수록 오차가 작아서 더 발견하기 어렵습니다.

날짜 변환 로직은 헬퍼 함수 하나로 중앙화하고, 호출하는 쪽에서 직접 `new Date()`를 쓰지 않도록 강제하는 것이 가장 확실한 방어입니다. 이번에 4곳이 모두 같은 방식으로 잘못되어 있었다는 것은, 복붙 코드가 같은 버그를 전파한다는 교과서적인 사례이기도 합니다.

### 수정 전에 현재 동작을 먼저 확인할 것

GA4 SPA 트래킹을 직접 추가했다가 Enhanced Measurement와 중복 발화되어 revert한 것은, "현재 무엇이 동작하고 있는지" 확인하지 않고 코드를 추가한 결과입니다. 트래킹 영역은 특히 이런 실수가 잦습니다. GA4, GTM, Mixpanel 같은 도구들은 내부적으로 많은 것을 자동 처리하고 있어서, 수동으로 같은 이벤트를 추가하면 중복이 발생하기 쉽습니다.

새 트래킹 코드를 추가하기 전에, 브라우저 개발자 도구의 네트워크 탭이나 각 도구의 디버그 모드로 현재 어떤 이벤트가 발화되고 있는지 먼저 확인하는 것이 안전합니다.
