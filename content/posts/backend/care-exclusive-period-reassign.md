## 두 서비스에 걸친 문제

인톡 케어에서 GA(보험대리점)는 설계사 후보자를 구매하고 온보딩한다. 케어는 전임 담당자가 만든 서비스를 7월 말에 넘겨받은 것이고, 크레딧 결제 자체는 내 작업이 아니다. 아래 두 버그는 그 구매 경로에서 나왔다. 파트너스는 케어의 온보딩 상태를 5분마다 읽어서 자기 화면에 보여준다.

## 독점이 영원히 풀리지 않았다

후보자를 구매한 GA에게는 독점 기간이 있어야 한다. 기존 구현은 상태 기반이었다. 구매되어 온보딩 중인 후보자는 다른 GA의 목록에서 계속 빠졌고, 시간이 지나도 돌아오지 않는 "무한 독점"이었다.

이것을 7일 시간 기반으로 바꿨다(BE-BUG-011, #269).

- 즉시 매칭(`auto_approved`)으로 구매될 때 `CreditService`가 `exclusiveUntil = now + 7일`을 저장한다.
- 예약 매칭을 관리자가 승인할 때도 `AdminRepository`가 같은 값을 저장한다.
- `AgentService`의 후보자 목록 필터에 `exclusiveUntil > now` 조건을 넣었다. 독점이 끝난 후보자는 다른 GA에게 다시 보인다.

세 파일에 11줄을 더했다. 구매가 확정되는 두 지점에서 만료 시각만 적도록 했다.

## 재배정하자 이전 온보딩이 살아 있었다

독점이 풀려 다른 GA가 같은 후보자를 구매하면 새 온보딩이 생긴다. 그런데 이전 GA의 온보딩 기록이 활성 상태로 남아 있었다. 같은 후보자에 온보딩이 두 개인 상태다.

`OnboardingStatus`에 `reassigned`를 터미널 상태(더는 전이하지 않는 상태)로 추가했다(BE-BUG-012, #271). 구매 경로가 네 갈래(크레딧 단건, 크레딧 벌크, 수동 매칭, 예약 매칭 승인)라서 네 곳 모두에서 새 온보딩을 만들기 전에 같은 후보자의 다른 GA 활성 온보딩을 `reassigned`로 바꾼다. 온보딩 목록과 통계는 `reassigned`를 제외한다.

## 파트너스 화면에서는 이름이 5분마다 바뀌었다

두 온보딩이 남아 있는 동안 파트너스 쪽에서 증상이 보였다. 재배정된 후보자의 GA 이름이 5분마다 이전 GA와 새 GA로 번갈아 표시됐다(BE-BUG-041).

파트너스의 5분 크론은 케어에서 온보딩을 받아 `deduplicateByUser()`로 후보자당 한 건만 남긴다. 비교 기준이 `agentId`였는데, 이 필드는 후보자 ID라서 같은 후보자의 레코드끼리는 항상 같은 값이다.

```typescript
// 변경 전: agentId는 같은 후보자끼리 항상 같아서 조건이 항상 false
if (!existing || agent.agentId > existing.agentId) { ... }

// 변경 후
if (!existing || new Date(agent.purchasedAt) > new Date(existing.purchasedAt)) { ... }
```

비교가 의미가 없으니 API 응답의 첫 레코드(`updatedAt` 내림차순)가 그대로 골라졌다. 관리자가 이전 GA의 온보딩을 수정하면 그 레코드의 `updatedAt`이 갱신되어 다음 크론에서 이전 GA가 선택됐고, 다음에는 다시 새 GA가 선택됐다. 기준을 `purchasedAt`으로 바꿔 가장 최근에 구매된 레코드, 즉 최신 GA 배정이 항상 이기게 했다.

원인이 둘이었다. 케어에는 이전 온보딩을 닫는 로직이 없었고, 파트너스에는 최신을 고르는 비교가 틀려 있었다. 파트너스 쪽만 고치면 케어의 데이터는 여전히 이상한 채로 남고, 케어 쪽만 고치면 이미 만들어진 중복 레코드가 계속 읽힌다. 티켓도 둘로 나눠서 서로 참조하게 했다.

## 남은 것

- 이미 잘못 동기화된 데이터를 일괄 보정하는 작업은 이번 범위에서 뺐다.
- 두 시스템이 5분 폴링으로 상태를 맞추는 구조는 그대로다. 구매 직후 5분까지는 파트너스 화면이 이전 상태일 수 있다.
- 구매 경로가 네 갈래라서, 다섯 번째 경로가 생기면 `reassigned` 처리를 같이 넣어야 한다.
