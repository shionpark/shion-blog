## 배경

인톡 케어에서 GA(보험대리점)가 후보자를 구매하면, 그 다음 단계는 "연계"다. 후보자에게 연락하고 미팅을 잡고 최종적으로 소속 설계사로 온보딩하는 과정이다.

문제는 이 흐름이 일직선이 아니라는 점이었다. 개인정보 제3자 제공 동의(이하 3자 동의) 여부에 따라 할 수 있는 일이 달랐다.

- **3자 동의 완료**: GA가 즉시 후보자 연락처를 확인하고 연락할 수 있다
- **3자 동의 미완료**: 관리자가 먼저 후보자에게 동의를 받아야 하고 그동안 GA는 기다려야 한다

같은 구매 완료 상태인데, 사용자가 할 수 있는 행동이 다른 상황이었다.

## 분기를 어디에서 처리할 것인가

처음에는 프론트엔드에서 분기하려고 했다. 구매 API 응답에 `thirdPartyConsent` 플래그를 내려보내고 화면에서 조건부로 다른 UI를 보여주는 방식이다. 하지만 이렇게 하면 같은 온보딩 목록에 성격이 다른 두 종류의 항목이 섞이고 상태 관리가 복잡해졌다.

결국 구매 시점에 서버에서 분기를 결정하도록 했다:

```typescript
// partners-be: care-application.service.ts
const endpoint = agent.thirdPartyConsent
  ? '/api/v2/applications/member'      // 즉시 매칭 (auto_approved)
  : '/api/v2/applications/non-member'; // 예약 매칭 (pending_approval)
```

3자 동의가 `true`면 케어 시스템이 즉시 GA 매칭을 시작한다(`auto_approved`). `false`면 관리자 승인 절차를 거친 뒤 예약 매칭이 진행된다(`pending_approval`). 상태 전이의 분기점을 서버에 두니까, 프론트엔드는 현재 상태에 맞는 UI만 보여주면 됐다.

## 온보딩 상태 설계

케어 DB의 `OnboardingStatus` enum은 10개 값을 가진다:

```prisma
enum OnboardingStatus {
  pending             // 연락대기
  contacting          // 연락중
  completed           // 완료 (레거시)
  failed              // 실패 (레거시)
  contact_failed      // 연락실패
  meeting_scheduled   // 미팅예정
  meeting_completed   // 미팅성공
  meeting_failed      // 미팅실패
  package_purchased   // 패키지구매건
  reassigned          // 재배정됨
}
```

실제로 활성 상태로 쓰는 건 7개(pending ~ package_purchased)다. `completed`와 `failed`는 초기 버전에서 쓰던 레거시 상태로, 기존 데이터 호환을 위해 enum에 남겨둔 것이다.

여기에 가상 상태가 하나 있다. 온보딩 완료 후 문제가 생기면 AS 요청이 들어오는데, 활성 AS 요청이 있는 온보딩은 DB 상태와 무관하게 AS 처리중으로 표시한다. 별도 상태를 만들지 않고 AS 요청의 존재 여부로 판단하는 방식을 택했다. 상태를 하나 더 추가하면 전이 경로가 늘어나지만 AS는 현재 이 건에 이슈가 있다는 플래그에 가깝기 때문이다.

## 상태 전이: 제한보다 추적

초기 설계에서는 상태 전이에 방향 제한을 두려고 했다. "미팅성공 → 연락대기"로 되돌리는 건 논리적으로 이상하니까. 하지만 실제 운영에서는 잘못 눌러서 상태를 변경한 경우가 있었고 되돌릴 수 없으면 관리자에게 CS가 들어왔다.

7개 활성 상태 간 자유로운 전환을 허용하되(같은 상태로 전이하는 것만 차단), 모든 변경을 로그에 기록하는 방향으로 바꿨다. 시스템이 실수를 막는 대신 실수를 추적할 수 있게 했다.

유일한 터미널 상태는 `reassigned`다. 같은 후보자를 새로운 GA가 구매하면 기존 GA의 온보딩이 자동으로 재배정 처리되는데, 이 상태에서는 어떤 전이도 불가능하다:

```text
GA-A가 후보자 X를 구매 → 온보딩 생성 (pending)
    ↓ (7일 독점 기간 경과)
GA-B가 같은 후보자 X를 구매
    → GA-A의 온보딩: reassigned (터미널, 전이 불가)
    → GA-B의 온보딩: 새로 생성 (pending)
```

이 처리가 필요했던 이유는 "핑퐁 방지"였다. reassigned 없이 새 GA에게 온보딩을 생성하면, 기존 GA의 활성 온보딩과 새 GA의 온보딩이 동시에 존재하게 된다. 두 GA가 같은 후보자에게 연락하는 상황이 생긴다.

## 7일 독점 기간

구매 후 7일간 해당 후보자는 다른 GA의 검색 결과에서 숨김 처리된다. 구현은 `exclusiveUntil` 필드로 했다:

```typescript
// 즉시매칭(auto_approved) 시
exclusiveUntil = now + 7일

// 예약매칭 승인 시
exclusiveUntil = now + 7일

// 후보자 목록 필터
where: { exclusiveUntil: { gt: now } }  // 독점 기간 중인 후보자 제외
```

기존에는 상태 기반으로 무한 독점이었다(온보딩이 활성 상태이면 계속 독점). 시간 기반 독점으로 전환한 이유는, GA가 구매만 해놓고 연락하지 않는 경우에 후보자가 무기한 묶이는 문제를 방지하기 위해서다. 7일이 지나면 독점이 자동으로 풀리고 후보자는 다른 GA에게 재공개된다.

7일이라는 기간은 연락하고 미팅 잡기에 충분한 시간을 기준으로 정했다. 너무 짧으면 GA가 압박을 느끼고 너무 길면 후보자가 묶여서 다른 기회를 잃는다.

## 구매 전/후 정보 경계

온보딩 상세 페이지에서 보여주는 정보 범위를 정하는 것도 설계 판단이었다:

- **구매 전** (검색 결과): 이름, 나이, 성별, 지역, 매칭 스코어, 등급
- **구매 후** (온보딩 상세): 위 정보 + 연락처(전화번호, 이메일), 자기소개, 유입 광고 정보

전화번호는 마스킹 처리해서 보여주되 복사 가능하도록 했다. 완전히 공개하면 크레딧 과금 모델의 의미가 약해지고 너무 숨기면 연락하는 데 불편하다.

## 트레이드오프

법적 요건(3자 동의)이 두 가지 흐름을 만들었고 이를 서버 분기로 처리하니 프론트엔드는 단순해졌다. 대신 서버가 매칭 로직의 분기점을 전부 가져가면서 케어 서비스의 비즈니스 로직 복잡도가 올라갔다.

상태 전이를 자유롭게 허용한 것은 이론적 정합성을 포기한 결정이다. "미팅성공 → 연락대기"가 논리적으로는 이상하지만 실수를 되돌릴 수 없어서 CS가 오는 비용이 더 컸다. 자유도를 주되 로그로 투명하게 관리하는 편이 운영 비용이 낮았다.
