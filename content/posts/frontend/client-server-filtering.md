## **데이터 필터링 로직을 어디에서 처리해야 할까?**

현재 프로젝트의 대부분의 도메인에는 데이터 배열을 받아 **테이블** 형태로 생성하는 기능이 있다.

개발 초기 단계에서는 CRUD를 우선순위로 두고 빠르게 작업했기에, API 요청시 설정하는 파라미터를 두고 큰 코민을 하지 않았다.

```typescript
export const fetchNotices = async ({ branchName, types, statuses } : INoticeListQuery) =>
  client.get<INoticeListResponse>(NOTICES.RUD, { branchName, types, statuses });
```

### 고민의 시작

그런데 공지사항 기능 구현 중, 
공지 상세 페이지에서 이전글 또는 다음글 버튼을 눌러 상세 페이지를 이동할 때마다
이전글 또는 다음글의 공지 제목이 깜빡이는 현상이 발생하면서 고민이 시작되었다.

데이터를 받아오는 속도가 화면이 렌더링 되는 속도보다 느려져서 발생하는 문제였는데,
그렇다면 ‘**전체 데이터를 받아오고 프론트에서 필터링 로직을 처리하는 게 더 사용성이 좋지 않을까?**’ 생각이 들었고,

다른 도메인도 마찬가지로 필터 조건이 점점 더 추가되면서 파라미터가 늘어남에 따라,
매번 서버에 다른 파라미터로 데이터 요청을 보내는 것보다 한 번의 요청으로 전체 데이터를 불러오고 
화면에서 이를 마음껏 사용하는게 서버에도 부하가 가지 않고 사용성도 더 좋아지지 않을까 생각이 들었다.

> 📝 **파라미터**(Parameter)는 **데이터를 필터링하는 조건**이다.

### 일반적인 데이터 필터링 구현 방법

내 생각과 다르게 일반적으로 가장 많이 사용하는 방식은 서버에서 필터링을 하는 것이다.

단순히 사용성에만 초점을 맞추면 클라이언트 필터링 방식이 좋아보이지만, 이를 제외한 많은 점에서 서버 필터링이 더 효율적이라는 것을 알 수 있었다.

- **클라이언트****에서 필터링: **서버에서 전체 데이터를 불러와 클라이언트에서 처리
- **✅ ****서버****에서 필터링: **필터 조건을 파라미터로 전달하여 서버에서 필터링된 데이터를 받아옴


대표적으로 서버 필터링의 장점은, 접근 권한에 따라 데이터를 불러올 수 있다는 점이었다.

관리자에게는 모든 데이터를 보여주되, 트레이너에게는 지점 및 직원 데이터를 제한할 수 있다.

회원 데이터가 3,000명 이상인 지점이 있다는 것도 서버 필터링을 채택한 이유가 될 수 있다.

1. **초기 로딩 속도가 빠르다**. 필요한 데이터만 가져오기 때문이다.
1. **성능이 안정적**이다. 데이터가 많아져도 서버와 DB에서 최적화된 방식으로 처리할 수 있다.
1. **데이터 동기화**가 가능하다. 실시간으로 변경된 데이터를 즉시 반영할 수 있다. 
클라이언트에서 필터링할 경우, 서버의 데이터와 클라이언트가 가진 데이터 사이에 불일치가 발생할 수 있다.
1. **권한 관리**가 쉽다. 필터링과 페이지네이션 로직에 권한 검사를 포함하여 사용자별로 적절한 데이터만 제공할 수 있다.


예를 들어, 관리자에게는 모든 데이터를 보여주되, 트레이너에게는 지점 및 직원 데이터를 제한할 수 있다.

여기에 더해 **보안과 데이터 노출 최소화**, **중앙화된 비즈니스 로직 관리** 등의 이점도 있다.



그렇다면 클라이언트 측 필터링의 장점은 무엇일까?

1. 서버 요청 횟수가 줄어 통신 비용이 절감된다.
1. 필터링 반응 속도가 빠르다. 버튼 클릭 시 즉각적으로 결과를 보여줄 수 있다.
1. 개발이 빠르다. 단순한 클라이언트 로직으로 구현할 수 있기 때문이다.


클라이언트 측 필터링은 다음과 같은 경우에 고려해볼 만하다: 데이터 규모가 작고(100~200개), 데이터 변경이 드물며, 필터링 조건이 단순하고, 서버 통신 비용을 최소화해야 할 때.

일반적으로는 2번, 즉 백엔드 필터링 방식을 선호한다.

1번 방식은 데이터가 늘어날수록 초기 페이지 로딩이 느려져 사용자 경험이 저하될 수 있다.

또한 DB 조회 시 제한 없이 모든 데이터를 가져와야 해서 서버 부하와 비용이 증가한다.

다만 Next.js 같은 SSR(서버 사이드 렌더링) 프레임워크를 사용한다면 상황이 달라질 수 있다!

빌드 시점에 모든 필터 조합의 정적 페이지를 미리 생성해두면 통신 비용과 초기 렌더링 문제를 해결할 수 있다.

단, 이 방식도 데이터가 적을 때만 유효하다. 데이터 증가가 예상된다면 피하는 것이 좋다.

결국 2번 방식의 장점이 1번의 단점을 상쇄할 만큼 강력하다고 판단했다.

그래서 우리도 2번 방식으로 개발을 진행해왔다.

하지만 공지사항 기능을 개발하면서 1번 방식을 고민하게 됐다.

이전글, 다음글 기능에서 필터링된 데이터를 실시간으로 보여줘야 하는데, 그 응답 속도가 느리다는 문제 때문이었다.
