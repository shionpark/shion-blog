## 용어 정리의 필요성

렌더링, DOM, API, 캐시, HTTP… 자주 쓰면서도 명확하게 이해하지 못하는 프론트엔드 용어들이 있다. 이 글에서는 "주소창에 URL을 입력하면 무슨 일이 벌어지는가?"라는 질문을 따라가며 브라우저가 페이지를 보여주기까지의 전 과정을 정리한다.

## 브라우저란

브라우저는 HTML, CSS, JS를 렌더링해 웹페이지를 보여주는 애플리케이션이다. Chrome, Edge, Safari, Firefox 등이 대표적이다.

- **HTML**은 문서 요소를 구조화한 뼈대
- **CSS**는 스타일을 입히는 피부
- **JS**는 동적인 요소를 작동시키는 뇌

렌더링은 이 코드를 화면에 그리는 과정이다. 각 브라우저마다 렌더링 엔진이 있어 HTML 파일을 받아 브라우저 화면에 그려낸다.

프론트엔드 개발자로서 이해해야 할 핵심은 두 가지다. 브라우저의 렌더링 엔진이 **HTML 파일을 받기까지의 과정**과, 받은 이후에 **어떤 처리를 거쳐 화면에 그려내는지**.

## DNS 조회

사용자가 주소창에 URL을 입력하면 해당 URL 주소를 DNS(Domain Name System)에서 조회하여 IP 주소를 획득한다. URL은 사람이 읽을 수 있는 구조화된 주소, IP 주소는 서버의 실제 주소다.

하지만 매번 DNS 서버까지 조회하지는 않는다. 브라우저는 이전에 조회한 도메인-IP 매핑을 캐싱해두고 재사용한다.

- **브라우저 DNS 캐시** — 브라우저 내부에 저장
- **OS DNS 캐시** — 운영체제 차원에서 저장
- **ISP DNS 캐시** — 통신사 DNS 서버 차원에서 저장

캐시에 있으면 DNS 서버를 조회하지 않고 바로 IP 주소를 사용한다. 같은 사이트를 재방문할 때 빠르게 연결되는 이유다.

## TCP 연결

DNS 조회로 IP 주소를 알아내면 브라우저는 TCP(Transmission Control Protocol) 연결을 맺어 서버와 통신한다. SSL을 사용하는 경우 TLS Handshake가 이루어지는데, 서버와 브라우저가 암호화 통신을 설정하는 과정이다.

## HTTP 요청과 CDN

서버 연결 후 HTTP 요청을 보내고 해당 URL의 HTML 파일을 응답받는다.

여기서 서버란 웹 애플리케이션을 운영하는 기업이 데이터를 저장해두고 요청이 들어올 때마다 응답해주는 장치다. 카카오 데이터 센터, 구글 데이터 센터처럼 물리적인 실체가 있다.

구글의 원(origin) 서버는 미국 본사에 있다. 우리나라에서 요청을 보내면 물리적 거리만큼 시간이 더 걸린다. 이를 줄이기 위해 CDN(Content Delivery Network)이 존재한다. 전 세계에 분산된 엣지 서버가 원 서버의 콘텐츠를 캐싱해두고 사용자와 가장 가까운 서버가 응답을 처리한다.

CDN의 효과:

- **지리적 지연 최소화** — 서울 사용자는 서울 엣지 서버에서 응답을 받는다
- **대규모 트래픽 분산** — 원 서버에 부하가 집중되지 않는다
- **보안 강화** — DDoS 방어, TLS 암호화 지원

CDN 외에도 포워드 프록시, 리버스 프록시, API 게이트웨이 같은 중간 계층이 존재한다.

## 리소스 캐싱

서버에서 받아온 HTML, CSS, JS, 이미지 같은 정적 리소스를 브라우저가 캐시 저장소(메모리/디스크)에 저장했다가, 같은 요청이 들어오면 재사용한다. `Cache-Control`, `ETag`, `Expires` 같은 HTTP 헤더로 캐싱 동작을 제어한다.

모든 리소스가 영원히 변하지 않는 것은 아니므로, 리소스가 변하기 전까지만 캐싱하고 변한 이후에는 갱신하는 것이 중요하다.

## 브라우저 렌더링

서버로부터 받은 HTML 파일을 브라우저의 렌더링 엔진이 처리한다.

1. **DOM 생성** — HTML 파일을 파싱해 DOM(Document Object Model) 트리를 만든다
1. **CSSOM 생성** — CSS 파일을 파싱해 CSSOM(CSS Object Model) 트리를 만든다
1. **렌더 트리 생성** — DOM과 CSSOM을 결합해 화면에 실제로 표시할 요소만 담은 렌더 트리를 구성한다
1. **레이아웃** — 각 요소의 위치와 크기를 계산한다
1. **페인트** — 계산된 결과를 픽셀 단위로 화면에 그려낸다

이 과정을 **Critical Rendering Path**라 부르며 JS 파일은 DOM 파싱 중에 만나면 실행된다. `<script>` 태그의 위치와 `async`/`defer` 속성에 따라 렌더링 차단 여부가 달라지는 이유가 여기에 있다.

## 정리

URL을 입력하면 브라우저는 다음 순서로 페이지를 보여준다.

- **DNS 조회** — 도메인을 IP 주소로 변환 (캐시 우선 확인)
- **TCP 연결** — 서버와 통신 채널 확보
- **HTTP 요청** — HTML 파일 응답 (CDN이 가까운 서버에서 처리)
- **리소스 캐싱** — 정적 리소스를 저장해 재방문 시 재사용
- **렌더링** — DOM → CSSOM → 렌더 트리 → 레이아웃 → 페인트

캐싱은 이 흐름의 여러 단계에 개입하며 같은 파일을 다시 받지 않고(리소스 캐싱), 같은 도메인을 다시 조회하지 않고(DNS 캐싱), 먼 서버까지 가지 않도록(CDN 캐싱) 성능을 끌어올린다.
